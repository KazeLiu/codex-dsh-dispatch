## 用菜单写进 AGENTS.md（推荐）

手工粘贴容易漏、也不便于以后更新。用接入向导写入托管区块：

```cmd
codex-dsh-dispatch
```

选「写入协作提示词到 AGENTS.md」，再选范围：

- **全局**：`CODEX_HOME` 指向的目录（缺省 `~/.codex`）下的 `AGENTS.md`，对所有项目生效。
- **当前目录**：当前工作目录下的 `AGENTS.md`，只对这个项目生效。

写入的内容固定包在一对标记之间：

```markdown
<!-- codex-dsh-dispatch begin -->
## Codex 与 DSH 协作
...
<!-- codex-dsh-dispatch end -->
```

托管范围**只有这一对标记之间**：

- 重复写入是幂等的，只替换自己那一块，区块外内容与换行保持不变。
- 移除时也只删这一块；你自己写的同名小节原样保留。
- 标记不成对（多一个开始、少一个结束）或文件读不出来时直接报错、不写盘，不做猜测性修复。
- 同目录若存在 `AGENTS.override.md`，它的优先级更高。向导会提示「写了可能不生效」并要你再确认一次，不会在内容被覆盖的情况下报成功。

写入后需要让 Codex 重新读取 AGENTS.md（新开对话或按客户端方式重载）才生效。

## 补充时用 queue 还是 steer

`dsh_send` 的 `text` 有一个 `mode` 参数，决定这段文字怎么进 DSH 的会话：

| mode | 行为 | 什么时候用 |
| --- | --- | --- |
| `queue`（缺省） | 排队，等当前回合结束后再执行 | 会话已经跑完、要它返工；或者这是下一个独立步骤 |
| `steer` | 插进当前正在执行的回合 | 会话还在跑，发现方向偏了、漏了约束、要补资料 |

要点：

- 不写 `mode` 和写 `mode: "queue"` 完全等价，老调用不用改。
- `steer` 由宿主在可接受的边界注入，**不保证立刻打断正在执行的工具调用**；受理（`accepted`）也不代表已经生效。仍然要用 `dsh_wait` 观察结果，不要因为受理就认为改好了。
- `reply` 走的是宿主的提问回答通道，不能同时指定 `mode`，一起给会报 `invalid-argument`。
- 同一个 `requestId` 换了 `mode` 会被当成不同的提交并拒绝，避免同一个请求被两种方式重复投递。

## 手工版本（不想用菜单时）

把下面这段加进项目根目录已有的 `AGENTS.md`，与项目原有约定放在一起：

```markdown
## Codex 与 DSH 协作

- Codex 负责总体规划、技术决策、代码审查、bug 纠正和最终验收；细节实现默认通过 DSH MCP 委派，无需逐次确认委派。
- 派单传入当前实际工作目录、允许修改范围、必要资料、操作限制和完成条件。未明确指定时，模型与思考强度沿用桥接默认值。
- 使用 dsh_start / dsh_wait / dsh_send / dsh_cancel 完成派单、等待、原会话返工和显式取消；接收确认或等待超时都不代表任务完成。
- 会话还在跑时用 dsh_send 的 steer 纠偏或补方向；跑完后的返工与独立下一步用缺省的 queue。steer 不保证立刻打断工具调用，受理不等于生效。
- DSH 执行时，Codex 不同时改写它负责的代码。Codex 确认 DSH 停止写入后可直接修小范围 bug；较大返工交回原 DSH 会话。
- Codex 必须审查实际代码与差异，遵守本项目的测试、安装、提交及其他授权约定；工具不可用或需要人工批准时明确说明。
```

## 分工和执行顺序

1. **Codex 先判断方向。** 阅读相关代码和项目约定，给出最小充分方案，确定允许修改的位置、依赖与验收条件。
2. **DSH 实现。** Codex 使用 `dsh_start` 传入本次完整任务和绝对工作目录。插件关联工作区并创建本次对话专属的 DSH 会话。
3. **Codex 等待。** 使用返回的会话、请求 ID 和游标调用 `dsh_wait`。`accepted` 只表示接收；等待超时继续等待同一请求，不重复派单。
4. **Codex 审查与纠错。** 读取真实代码、调用关系和 Git 差异。任务还在跑时用 `dsh_send` 的 `steer` 及时纠偏；小修正由 Codex 接手；较大返工用缺省的 `queue` 回到原 DSH 会话，不另开一个失去上下文的任务。
5. **Codex 交付。** 对照完整需求检查结果，说明实际验证证据与影响使用的缺口。测试、构建、安装、提交和推送分别按用户本次授权执行。

DSH 写入某段代码时，Codex 只读该范围。Codex 接管之前，要确认 DSH 当前回合已停止；需要终止执行时显式调用 `dsh_cancel`，不能把一次等待超时当成已停止。

DSH 的工作目录、源权限和必要操作限制应在派单中明确。Codex 的全局指令、工具、浏览器、技能和完整对话不会自动复制到 DSH；需要的约束与材料由 Codex 在任务中传递，项目文件仍由 DSH 在同一目录中读取。

模型、强度和权限的默认值由桥接设置决定（`codex-dsh-dispatch config`），派单里显式指定时以本次为准。能从当前 Codex 会话读到三档权限就同步给 DSH，读不到时用桥接默认值，不假设已获得完全访问。

## 在其他项目重复使用

每个项目可以各自写入当前目录的 `AGENTS.md`，也可以只在全局写一次让所有项目生效。也可以把该流程封装成 Codex skill；无需为每个项目安装新的 DSH 实例或改写模型默认配置。MCP 提供能力，提示词、项目规则或 skill 决定何时调用它。

## 当前使用限制

- 当前对话没有加载到 `dsh_start` 等工具时，先让 Codex 重新加载 MCP 连接；仅登记配置不代表旧对话的工具清单已经更新。本机 stdio 代理链路已实际跑通。
- 人工审批目前在 DSH 中处理；提问回复、取消及重载恢复的完整真实联调范围见仓库内的 `docs/ACCEPTANCE.md`（不随 npm 包发布）。
- 自动委派在当前 Codex 回合中进行；结束回合或关闭 Codex 后，不保证 DSH 完成会自动唤醒 Codex 继续审查。

模型、强度和默认权限的 CMD 设置方法见 [安装与接入](INSTALL.md)。
